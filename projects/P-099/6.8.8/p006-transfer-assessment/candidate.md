# Phase D — Independent technical defense exercise

**Scenario** · Cedar Exhibit Booking

**Curriculum** · Preparatory transfer from P-006 to the independent technical defense in 6.8.8. This exercise uses a single authorized lab. [Canonical work packages](../../../../strategy/334-sublayers.md)

Cedar Exhibit Booking serves two fictional venues. Each has a different operator and reviewer. An operator drafts a maintenance notice from private notes. “Tell the venue team” could mean the reservation desk or the internal support group. Those audiences may see different fields. A ready preview is permitted only for the reservation desk inside the lab. The support reference is fictional private data. Use the exact two-venue fixture and record which information can reach each identity and destination. [Synthetic fixture](fixture.json)

## Working conditions

Use a newly configured, isolated application you are authorized to operate. Record the authorization, exact implementation and model versions, allowed synthetic actors, model route, storage and destinations. Keep any account secret out of the submission. Use only synthetic input and a local delivery boundary.

Complete the essential assessment, configuration, implementation, testing, scoring and explanation without AI assistance. Official documentation and the authorized app's source are permitted. The earlier P-006 implementations and scorers are study material. This is a transfer exercise, so develop and explain your own approach for the new venue and reviewer boundaries. The generated candidate brief is separate from your independent work.

## Assignment

1. Inventory the app, accounts and service identities, assets, operations and effective permissions. Show which path carries private notes to the approved model and which paths carry preview data or operational metadata.
2. Define the two venue policies and your oracles before execution. Evaluate legitimate ambiguous, explicit and incomplete requests. Track the model's reply separately from any backend state. Preserve failures and inconclusive runs.
3. Configure or implement a server-owned preview control. Show how an approved reservation-desk preview is derived, how owner and reviewer authority is scoped to a venue and revision, and what happens when the model is wrong. Exercise ordinary authorization decisions with your synthetic test identities.
4. Demonstrate the approved operational fields on a working event or logging route. Compare protected content at its approved private location with the operational record. Check the declared 30-second private-candidate lifetime and covered data copies through separate observations.
5. Write the technical and executive reports. Explain what was actually assessed, observed effects, unsupported claims, residual risks and retest evidence. Mark unexercised paths with the appropriate status and a specific evidence gap.

## Submission artifacts

| Artifact | Minimum evidence |
| --- | --- |
| Scope and architecture | Authorizing context, version pins, permitted actors and destinations, architecture and trust boundaries, identity and asset inventory and operation permissions. |
| Policy and test plan | Prewritten requirements, acceptance criteria, exact fixtures and comparisons, and a plan for checking which target produced each result. |
| Implementation and configuration | Reviewable code and reproducible pinned configuration for the assessed deployment, plus its ordinary usage instructions. |
| Execution record | Genuine commands, observed state, exact requests and replies, run IDs, UTC timestamps, artifact hashes and separately obtained backend or destination receipts. |
| Technical and executive reports | Findings with traceable evidence, incomplete coverage, remediation and retest where applicable, and a short summary a stakeholder can understand. |
| Technical defense | Your own explanation of one model result, one independent backend result and one remaining uncertainty. The assessor chooses an additional item from your evidence during review. |
